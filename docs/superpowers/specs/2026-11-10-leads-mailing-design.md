**Дата:** 2026-11-10
**Статус:** действующий; закрывает пункт §17 итоговой спецификации
(`2026-10-10-cms-final-specification.md`) «заявки и рассылка».

`src/server/lead-mail.ts`, `src/lib/lead-mail.ts`, `src/app/api/leads/route.ts`,

**Что делать с этим документом:** читать как ТЗ раздела. Спорные детали решаются по

## 1. Предмет и границы

Перенести в PHP-ядро CMS заявки с публичных форм: посетитель оставляет имя и контакт (телефон или
почту) из блока «Форма заявки» на странице конструктора, заявка записывается в базу, на почту
сразу уходит подтверждение приёма, администратор видит заявки в админке и отвечает письмом из
того же раздела.

**Входит:**

- таблица ядра `tbl_lead` и правила валидации полей заявки и ответа;
- публичная форма без JavaScript: секция конструктора вида `lead` + маршрут `POST /lead`;
- ловушка для ботов, согласие на обработку данных, лимит приёма с одного адреса;
- письма: подтверждение приёма (автомат) и ответ школы (из админки) через готовый
  `Cms\Core\Mailer`;
- админка `/admin/leads`: список с фильтрами, поиском и пагинацией, действия «ответить письмом»,
  «отметить обработанной / вернуть в новые», «удалить».

**Не входит:** массовая рассылка/подписки, очереди писем, правка контакта посетителя
администратором, личный кабинет заявителя. Подробнее — вердикт 9.1.

## 2. Данные

Миграция ядра `sql/0002_leads.sql` (только дополняющая, без `DROP`/`DELETE`/`ALTER DROP`):

```sql
CREATE TABLE IF NOT EXISTS tbl_lead (
  id              VARCHAR(26)  NOT NULL,
  name            VARCHAR(80)  NOT NULL,
  contact         VARCHAR(120) NOT NULL,
  message         TEXT         NULL,
  source          VARCHAR(120) NOT NULL DEFAULT '',
  status          VARCHAR(16)  NOT NULL DEFAULT 'NEW',
  done_at         DATETIME     NULL,
  confirm_sent_at DATETIME     NULL,
  reply_text      TEXT         NULL,
  reply_sent_at   DATETIME     NULL,
  created_at      DATETIME     NOT NULL,
  PRIMARY KEY (id),
  INDEX (status, created_at),
  INDEX (created_at)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS tbl_lead_attempt (
  id         BIGINT       NOT NULL AUTO_INCREMENT,
  scope      VARCHAR(120) NOT NULL,
  created_at DATETIME     NOT NULL,
  PRIMARY KEY (id),
  INDEX (scope, created_at)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- `tbl_lead.id` — `VARCHAR(26)` из `core/id.php` (`newId()`), сортируемый по времени: перенос
  данных из PostgreSQL (§17) не гарантирует порядок `AUTO_INCREMENT` при восстановлении.
- Колонки повторяют модель `Lead` портала; `source` — строка, а не внешний ключ: страницу могут
  удалить или переименовать, а обращение должно остаться. Контакт хранится открытым текстом —
  администратору нужно отвечать, ключ шифрования всё равно лежал бы рядом с базой (комментарий
  портала дословно).
- `tbl_lead_attempt` заменяет счётчик портала, который жил в памяти процесса Node. В PHP процесса
  между запросами нет, поэтому лимиты считаются по таблице: `scope` = `ip:<адрес>` для приёма и
  `reply:<id заявки>` для ответов (раздел 4). Старые строки не чистятся — как `tbl_login_attempt`.
- Даты пишутся `utcStamp()` в UTC; статусы — `VARCHAR` со словарём в PHP (`CHECK` в MySQL 5.7
  молча игнорируется).

## 3. Правила валидации и помощники (перенос из `src/lib/leads.ts`)

Константы и функции живут в `core/leads.php`:

- `LEAD_CONTACT_RE` — телефон (`[\d+][\d\s().-]{4,23}`) или почта (`…@домен.зона`), без `mailto:`.
- `LEAD_SOURCE_RE` — путь этого сайта без схемы и чужого домена, вложенность до четырёх уровней,
  до 80 символов в последнем сегменте, необязательные `?query` и `#якорь`.
- `LEAD_STATUS_NEW = 'NEW'`, `LEAD_STATUS_DONE = 'DONE'`, метки `Новая` / `Обработанная`.
- Пределы полей: имя 2…80; контакт 5…120 и по `LEAD_CONTACT_RE`; сообщение ≤ 1000 (необязательно);
  источник ≤ 120 и по `LEAD_SOURCE_RE`, иначе пустая строка; `company` (ловушка) ≤ 120.
- `leadIsEmail(contact)` — письмо уходит только на почту; телефон в том же поле означает
  «позвоните», кнопка ответа для него не показывается.
- `leadContactHref(contact)` — `mailto:` или `tel:` для списка админки; нестандартную строку
  ссылкой не делаем.
- Ответ администратора: `LEAD_REPLY_MIN = 10`, `LEAD_REPLY_MAX = 2000` символов.

## 4. Лимиты (перенос механики, смена хранилища)

Портал держал счётчик `tooManyRequests()` в памяти одного процесса Node. В PHP лимиты честно
переносятся в `tbl_lead_attempt` — «попытка» пишется строкой со `scope` и `created_at`, окно
считается запросом `COUNT(*) WHERE scope = ? AND created_at > ?`:

- приём заявки: `ip:<адрес>` — не чаще 5 в час (429-аналог — отказ с текстом «Заявки с одного
  адреса принимаются не чаще пяти в час. Попробуйте позже.»);
- ответ на заявку: `reply:<id>` — не чаще 3 за 10 минут, иначе «По этой заявке письма уже
  уходили — подождите десять минут».

Адрес берётся только из `REMOTE_ADDR` через `clientIp()` (правило `ClientIpTest`; за прокси все
посетители делят один лимит — сознательно, как в ядре для входа).

## 5. Публичная форма и маршрут

Вид `lead` добавляется в перечень ядра (`PAGES_KINDS`, `PAGES_KIND_NAMES` — «Форма заявки»,
24-й вид). Поля секции: `anchor`, `badge`, `title`, `lead_text`, `note`, `items` (пункты «что будет
после заявки»); общих картинки, кнопок и вёрстки у вида нет. Данные самой заявки в секции не
хранятся — их принимает и пишет только маршрут.

`theme/sections/lead.php` печатает две колонки: слева обещания из `items`, справа форму:

- поля «Как к вам обращаться» (имя), «Телефон или почта», «Вопрос» (необязательный textarea);
- скрытое поле `source` — текущий путь страницы + `#якорь секции` (для предпросмотра черновика —
  с `?draft=1`), как `sourceOf()` портала, но собранный сервером, а не `window.location`;
- скрытая ловушка `company` (человеку не показывается, классы `sr-only` и `aria-hidden`);
- чекбокс согласия на обработку персональных данных со ссылкой на `/privacy`;
- кнопка «Отправить заявку»; форма — обычный `method="post" action="/lead"` с `csrfField()`.

Форма работает без JavaScript. Отличие от портала (там `fetch('/api/leads')`) зафиксировано
вердиктом 9.2: в PHP CMS формы обязаны работать без JS, поэтому вместо JSON-ответа — классический
POST с PRG-редиректом обратно на страницу.

Маршрут ядра `POST /lead` (публичный, точка `before_route` не мешает):

1. `csrfCheck()`;
2. лимит приёма по IP (раздел 4);
3. валидация полей; ошибка — редирект на `source` с человеческим текстом в сессионном flash
   (набранный текст в форму не возвращается — форма живёт внутри секции, а не на своём экране;
   поля браузер оставляет при POST-редиректе только если бы не было PRG, поэтому отказ уходит
   через flash-причину, как экран «Приложения»);
4. ловушка: заполненный `company` — отвечаем тем же «спасибо», что и настоящему человеку, заявку
   не пишем (по ответу нельзя понять, сработала ловушка или нет);
5. запись `tbl_lead` (`status = NEW`, `source` нормализован `leadSourceOrEmpty()`);
6. если контакт — почта: синхронно отправляем подтверждение `leadConfirmMail()` через
   `Cms\Core\Mailer` и пишем `confirm_sent_at`; провал отправки пишется в журнал
   (`lead.confirm_failed`) и посетителю не показывается — обращение уже в базе;
7. PRG-редирект на `source` с `?notice=lead_sent` и `#якорем` (человек остаётся у формы и видит
   подтверждение).

## 6. Письма (перенос из `src/lib/lead-mail.ts`, `src/server/lead-mail.ts`)

Помощники в `core/lead-mail.php`:

- темы: «Заявка принята — {ИМЯ САЙТА}», «Ответ школы — {ИМЯ САЙТА}»;
- `leadEmailText()` — экранирование HTML письма (как `escapeHtml` портала: `& < > " '`) плюс
  перевод строки в `<br>`; имя из формы и текст ответа вставляются только экранированными;
- `leadConfirmHtml(name)` — приветствие по имени, текст «Заявку получили…»;
- `leadReplyHtml(name, text)` — приветствие и весь текст ответа администратора, ничего от себя;
- `leadReplyDraft(name)` — готовый черновик ответа (администратор правит, а не пишет с нуля);
- общий подвал письма дословно из портала.

Отправка — `Cms\Core\Mailer::send(['to' =>, 'subject' =>, 'text' =>, 'html' =>])`. Текстовое тело
(`text`) собирается из тех же строк, но без HTML-обёртки; `html` — из помощников выше. Письмо уходит
только на почту (`leadIsEmail()`); телефону письмо не отправляется.

## 7. Админка «Заявки»

Маршруты ядра `GET /admin/leads` и `POST /admin/leads` с правом `manage` (только администратор:
контакты — личные данные, портал зовёт `requireAdmin`). Пункт «Заявки» добавляется в `admin_nav`.

Экран `core/templates/admin/leads.php` (перенос `src/app/(app)/admin/leads/page.tsx`):

- заголовок «Заявки с публичных страниц (N)» и пояснение;
- фильтры-вкладки: Новые / Обработанные / Все; по умолчанию «Новые»;
- поиск по имени и контакту (`escapeLike`, спецсимволы ищутся как текст); подсказка «Имя или
  контакт»;
- таблица: Человек (имя + ссылка `leadContactHref`), Сообщение (переносы строк сохраняются),
  Откуда (`source` моноширинным), Когда (дата в русском формате через `core/date.php`; если
  обработана — «ответили …»), Что с заявкой (бейдж статуса и кнопки);
- пагинация 25 на страницу, «Страница X из Y · всего Z · на странице 25».

Действия (один POST-обработчик `op`, как на экране «Приложения»):

- `set-status` — `NEW ↔ DONE` (сохраняет `done_at` на `DONE`, снимает на `NEW`);
- `delete` — удаление вместе с контактами, с подтверждением текстом на кнопке; без JS подтверждение
  делается отдельной формой-экраном или атрибутом `onclick="return confirm(…)"` (решить при
  реализации; стражи зон нажатия не нарушать);
- `reply` — открывает форму ответа (или отдельный экран ответа без JS): textarea с черновиком
  `leadReplyDraft(name)`, счётчик «X из 2000 символов», кнопка «Отправить письмо»; валидация
  `LEAD_REPLY_MIN…MAX`; лимит 3/10 минут на заявку; письмо только на почту; после успеха —
  `reply_text`, `reply_sent_at`, `status = DONE`, `done_at`, PRG с `?notice=lead_reply_sent`.

Кнопка «Ответить письмом» показывается только когда `leadIsEmail(contact)`. Последний отправленный
ответ хранится (`reply_text`) и подставляется черновиком — повторное письмо правят, а не пишут с
нуля.

## 8. Уведомления и журнал

Словарь `LEAD_NOTICE_TEXT` в `core/notice.php`: `lead_sent` (публичное подтверждение приёма),
`lead_reply_sent`, `lead_status_saved`, `lead_deleted`. Каждый ключ обязан иметь кнопку, которая его
вызывает, и наоборот — страж `NoticeKeyTest`. Журнал: `lead.created`, `lead.confirm_sent`,
`lead.confirm_failed`, `lead.reply_sent`, `lead.reply_failed`, `lead.deleted`, `lead.status_saved`
(`logInfo`/`logWarn`/`logError`; в журнал не пишутся содержимое сообщения и тексты писем).

## 9. Вердикты (отступления от источника)

1. **«Рассылка» в §17 — это письма по заявкам, а не отдельная массовая рассылка.** В портале
   единственный почтовый контур заявок — подтверждение приёма и ответ школы; таблиц подписок или
   массовой рассылки нет. Вводить их означало бы новое требование, а не портирование, поэтому
   cron для очереди писем не нужен: подтверждение уходит синхронно в том же запросе, провал — в
   журнал. Если рассылка понадобится, у неё будет своя спецификация.
2. **Форма работает без JavaScript.** Портальная форма шлёт `fetch('/api/leads')`; в PHP CMS
   «каждый экран работает без JavaScript» (правило §6 итоговой спецификации), поэтому аналог —
   обычный POST на маршрут `/lead` с PRG-редиректом. Ловушка, согласие и пределы полей сохранены.
3. **Счётчик лимитов переносится из памяти в таблицу.** У PHP нет долгоживущего процесса; таблица
   `tbl_lead_attempt` — честный аналог `Map` портала и не теряет счётчик между запросами.
4. **Подтверждение приёма синхронное, а не фоновое.** Портальный `void confirmLead()` уходил в
   фоне того же процесса; в PHP фонового процесса нет, поэтому письмо отправляется в запросе
   после записи заявки, а провал не доходит до посетителя (обращение уже в базе).
5. **Отказ валидации возвращает текст ошибки, а не набранные поля.** Форма живёт внутри секции
   страницы, и набранный текст через PRG не провести; человек видит человеческую причину во
   flash-плашке рядом с формой. Это известное упрощение против портального fetch-сценария.
