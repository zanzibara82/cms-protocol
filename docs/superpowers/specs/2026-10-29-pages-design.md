# CMS-страницы из блоков и конструктор — дизайн слоя

**Дата:** 2026-10-29
**Статус:** разделы 1–7 подтверждены в мозговом штурме, ждёт вычитки человеком
**Основание:** спецификация `2026-10-10-cms-final-specification.md` §17 (первый раздел портирования:
«CMS-страницы из блоков и конструктор, включая живые блоки новостей»); источник —
`archives/english-portal` (`prisma/schema.prisma`: `Page`, `LandingSection`; `src/lib/landing.ts`,
`src/components/landing/sections.tsx`, `src/server/pages.ts`); прецедент точки расширения — дизайн
`2026-10-16-news-region-blocks-design.md`.

## Принятые решения штурма (перечень, чтобы не переспрашивать)

1. **Слой живёт в ядре** (как в портале, где `Page`/`LandingSection` — core-схема): «/» обязана
   отвечать и без единого приложения, конструктор страниц — способность сайта, а не раздел.
   Экраны конструктора сидят в `/admin` (право `manage`), таблицы — ядро (`sql/0002_pages.sql`).
   Установку кнопкой и выключение у слоя нет; вклады приложений выключаются вместе с ними.
2. **Главная — блоки без страницы**: секции главной живут той же таблицей с `page_id = ''`
   (не NULL — иначе уникальный ключ `(page_id, key)` допускает дубликаты ключей главной).
   Отдельной строки `Page` для главной нет; `coreHome` рисует секции вместо статической заглушки.
3. **Первый заход — каркас + базовые виды**: данные, публичный рендер, конструктор и семь видов
   ядра (hero, band, cards, steps, prose, cta, faq) + вклад живых новостей. Остальные виды портала
   (levels, demo, split, chain, banner, slider, video, pricing, toc, quote, review, related, gallery,
   float, table, tabs, files, contacts) добираются пачками следующими заходами; вид `lead`
   (форма заявки) сюда не входит — заявки и рассылка отдельный раздел §17.
4. **Вклады приложений — через фильтры**, повторяя форму `region()` (решение 1 дизайна 2026-10-16):
   ядро спрашивает `pages_block_kinds` (список вкладов) и зовёт `pages_block_<kind>` для рендера;
   news подписывается и рисует живую ленту по своим настройкам. Нового реестра вкладов в ядре нет.
5. **Меню (шапка/подвал) — отдельным заходом следом**; сейчас навигация остаётся статической
   в `theme/partials/header.php` и `footer.php`.
6. **Картинки — файлы на диске** в `public/uploads/images` (паттерн доски `upload.php`); в секциях —
   путь. Причина портала держать байты в базе (`LandingImage`) — standalone-образ — у CMS отсутствует.
7. **Старые адреса — по образцу новостей**: таблица старых слагов страниц + 301 на новый адрес.
   Адреса: страница занимает `/{slug}` одним сегментом; точные маршруты ядра и разделов
   (`/admin`, `/login`, `/logout`, `/news`, `/shop`, `/classifieds`, `/sitemap.xml`, `/robots.txt`,
   `/assets`, `/uploads`) зарезервированы — слаг не может совпасть с их первым сегментом, и ядро
   отдаёт страницы только там, где точный маршрут не сработал (роутер ставит точные раньше
   параметрических — это уже так).

## Границы слоя (чего он не делает)

- Не делает меню и не трогает статическую навигацию (заход следом).
- Не делает форму заявки и заявки: `kind` вида не существует, раздел §17 приедет со своим.
- Не добавляет видов, кроме семи базовых и вкладов: добор видов — свои заходы, а не накопление.
- Не кэширует секции и не вводит версионирование/черновики секций: сохранение честное, предпросмотр
  — прямым адресом у залогиненного администратора.
- Не вводит ролей: конструктор сидит на праве `manage`, как остальные экраны `/admin`.
- Не переносит `LandingImage` и редактирование картинок из админки: пути вписываются текстом,
  загрузка файлов — у разделов, у которых она уже есть.
- Не переопределяет решения пилота и дизайна 2026-10-16: `region()` и news-блоки работают как есть,
  на главной по-прежнему стоит `region('home')`.

## 1. Схема данных ядра

Ядро получает две таблицы релизом `sql/0002_pages.sql` (ядро применяет SQL из `sql/`, `coreSqlPending()`
— существующий механизм миграций ядра).

```sql
CREATE TABLE page (
  id          CHAR(32) NOT NULL PRIMARY KEY,
  slug        VARCHAR(80) NOT NULL,
  title       VARCHAR(120) NOT NULL,
  description VARCHAR(200) NOT NULL DEFAULT '',
  status      VARCHAR(16) NOT NULL DEFAULT 'DRAFT',
  noindex     TINYINT NOT NULL DEFAULT 0,
  created_at  CHAR(19) NOT NULL,
  updated_at  CHAR(19) NOT NULL,
  UNIQUE KEY page_slug (slug),
  KEY page_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE page_section (
  id         CHAR(32) NOT NULL PRIMARY KEY,
  page_id    CHAR(32) NOT NULL,          -- '' — секция главной «/»
  sec_key    VARCHAR(40) NOT NULL,
  kind       VARCHAR(40) NOT NULL,
  layout     VARCHAR(20) NOT NULL DEFAULT '',
  anchor     VARCHAR(40) NOT NULL DEFAULT '',
  badge      VARCHAR(80) NOT NULL DEFAULT '',
  title      VARCHAR(160) NOT NULL DEFAULT '',
  lead       TEXT NOT NULL,
  note       VARCHAR(200) NOT NULL DEFAULT '',
  image      VARCHAR(200) NOT NULL DEFAULT '',
  image_alt  VARCHAR(160) NOT NULL DEFAULT '',
  buttons    JSON NOT NULL,              -- [{label, href, blank, variant}]
  items      JSON NOT NULL,              -- повторяющиеся блоки вида
  settings   JSON NOT NULL,              -- настройки вклада приложения: ядро хранит, не понимает
  sort       INT NOT NULL DEFAULT 0,
  visible    TINYINT NOT NULL DEFAULT 1,
  updated_at CHAR(19) NOT NULL,
  UNIQUE KEY page_section_key (page_id, sec_key),
  KEY page_section_order (page_id, sort)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE page_old_slug (
  slug       VARCHAR(80) NOT NULL PRIMARY KEY,
  page_id    CHAR(32) NOT NULL,
  created_at CHAR(19) NOT NULL,
  KEY page_old_slug_page (page_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Отличия от портала, каждое — по причине:

- Колонка `key` переименована в `sec_key`: `key` — reserved-слово MySQL, и бездумный перенос заставит
  каждый запрос писать backticks.
- `oldSlugs[]` из Prisma становится таблицей `page_old_slug` — тот же образец, что `news_old_slug`;
  строка старого адреса ведёт на страницу, а не наоборот, чтобы историю адресов можно было показать.
- Секции главной — `page_id = ''`, а не NULL (решение 2 штурма): уникальный ключ в MySQL считает
  NULL всегда разным, и с NULL дубликаты ключей главной прошли бы мимо стража.
- `badge/title/lead/...` — `NOT NULL DEFAULT ''` вместо NULL: пустая секция честнее «нет значения»,
  и шаблон не расставляет `?? ''` по всем полям.
- Префиксы строк (status, kind, layout) — `VARCHAR` с перечнем в коде (решение 7 дизайна 2026-10-16,
  §8 пилота).
- Колонку `gallery` портала не переношу: вид `gallery` не в базовом наборе; приедет вместе с видом.

## 2. Публичный рендер

Ядро добавляет два маршрута в конец реестра — после всех точных маршрутов ядра и разделов:

- `GET /` — существующий `coreHome` перестаёт быть заглушкой: рисует секции главной
  (`page_id = ''`), а при их отсутствии оставляет нынешний текст «Сайт собирается на собственной
  CMS…» — пустая зона не ломает установку и демо-стенд. `region('home')` в `theme/home.php`
  остаётся: news-блоки главной работают как есть, вклад новостей встаёт в общий порядок секций.
- `GET /{slug}` — параметрический маршрут ядра. Точные маршруты реестра выигрывают по построению
  сортировки (`router.php` ставит статические раньше), поэтому разделы и служебные адреса
  неотторжимы. Слаг дополнительно проверяется формой и списком зарезервированных первых сегментов
  (решение 7 штурма) — страница не может занять `/news`, `/admin` и прочие даже без маршрутов.

Поведение адресов, повторяющее новости и портал:

- `DRAFT` отвечает 404 всем, кроме залогиненного администратора с правом `manage` — ему прямым
  адресом виден предпросмотр (в портале «DRAFT виден только редактору»).
- Смена слага пишет старый адрес в `page_old_slug`; ответ на старый адрес — 301 на новый, как у
  новостей. Слаг, переселившийся на другую страницу, снимает старую запись: адрес один.
- Метаданные, sitemap и noindex — бесплатно: `seo_meta` работает по пути (`/<slug>`), `coreSitemap`
  получает список опубликованных страниц, `noindex` страницы читается рендером.

## 3. Виды ядра первого захода

Семь видов по образцу `KIND_META` портала, каждый — частичный шаблон `theme/sections/<kind>.php`
и строгий разбор содержимого на сервере (в CMS разбора форм нет «на полках» — поля приносит
конструктор):

| вид     | поля                                                                         |
|---------|------------------------------------------------------------------------------|
| `hero`  | title, lead, note, image, image_alt, buttons                                 |
| `band`  | title, lead, note                                                            |
| `cards` | title, lead, items[{image, title, text, href, note}]                         |
| `steps` | title, lead, items[{title, text}]                                            |
| `prose` | title, lead (абзацы, e() построчно)                                          |
| `cta`   | title, lead, buttons                                                         |
| `faq`   | title, items[{title, text}] + JSON-LD FAQPage (как в портале)                 |

`layout` в первый заход не рисует вариантов: колонка есть, но значения пустые — варианты вёрстки
(cols-4/rows) приедут с добором видов. Неиспользуемые ядром `buttons/items/settings` — `JSON NOT NULL`
и всегда `[]`/`{}`, чтобы шаблон не ветвился на NULL.

Предел секций на одну страницу — константа `PAGES_SECTIONS_LIMIT = 40`: конструктор проверяет до
вставки и перечитывает при гонке; у news-блоков предел был в 6 на зону, здесь экран объёмнее.

## 4. Конструктор в /admin

Экраны на праве `manage`, по образцу существующих экранов ядра:

- `/admin/pages` — список страниц (слаг, статус, noindex, обновлено) + раздел «Блоки главной»
  со ссылкой на редактор главной; создание страницы — slug + title, дальше конструктор.
- `/admin/pages/{id}` (и `/admin/pages/home` для главной) — редактор секций: добавить секцию
  (вид из перечня), правка полей вида (тексты, кнопки, повторные items с добавлением/удалением
  строк), порядок вверх/вниз, видимость, удалить. Сохранение секции — POST с CSRF, как везде.
- Слаг правится на странице; при смене с проверкой занятости и списком зарезервированных сегментов.
  `description` страницы — прикладной текст для метаданных, а не повод лезть в seo-раздел.

Формы повторяющихся items — по образцу форм характеристик доски (строки с индексами, сервер
собирает и валидирует); никаких клиентских редакторов JSON, человек правит полями.

## 5. Вклад приложений (живые блоки новостей)

Форма — решение 4 штурма, повторяющая `region()`:

- Ядро спрашивает `applyFilters('pages_block_kinds', [])` — приложение отвечает списком вкладов
  `[{kind, name, fields}]` для конструктора (какие поля настроек рисовать).
- Рендер секции с чужим `kind`: ядро зовёт `applyFilters('pages_block_' . kind, '', settings, head)`
  (`head` — badge/title/lead/note/anchor секции); пустой ответ — секция не печатается вовсе
  (портал: «пустое место честнее чужого блока»).
- Приложение выключено — фильтров нет, страница живёт дальше без блока: выключение news снимает
  вклад без миграций, как и было с `region()`.
- News регистрирует вид «Новости — лента» (`kind = 'news_feed'`) с настройками `{count, category,
  layout}` по образцу своих блоков вывода; конструктор рисует его поля формой из ответа
  `pages_block_kinds`.

## 6. Транзакции, гонки, стражи

- Сохранение страницы и её секций — `tx()`; смена слага и запись старого адреса — одна транзакция
  (образец правки материала новостей).
- Уникальные ключи дают гонки двух одновременных сохранений (слаг страницы, ключ секции): catch
  со стражем `duplicateKeyException()` и человеческой причиной через `duplicateReason()` —
  механика, только что выведенная в ядре, применяется с первого дня слоя.
- Порядок секций — перечитывание `max(sort)+1` при вставке и перечитывание при гонке предела.
- Все SQL-запросы через `run()/one()/value()` с плейсхолдерами; JSON-колонки пишутся
  `json_encode(…, JSON_UNESCAPED_UNICODE)` по образцу `body` материала.

## 7. Что остаётся за пределами первого захода

- Меню шапки/подвала из базы (заход следом, таблица `page_menu` по образцу `MenuItem`).
- Доборы видов: levels, demo, split, chain, banner, slider, video, pricing, toc, quote, review,
  related, gallery, float, table, tabs, files, contacts — каждый пачкой со своими шаблонами.
- Заявки (`lead`) и рассылка — отдельный раздел §17.
- Перенос контента главной и страниц из `content-*.ts` портала — вместе с переносом данных
  из PostgreSQL, не здесь.
