# RELEASE 2.2 «Editorial Pro» — предварительный аудит

Документ фиксирует состояние NovaCMS до начала работ, точки интеграции редакционной системы
и решения по совместимости. Аудит выполнен по коду ядра, модулей `news`, `commerce`, `learn`,
`classifieds`, шаблонам админки, JavaScript конструктора и миграциям.

## 1. Как сейчас выполняется сохранение

### Страницы

- `core/pages.php` — единственный слой записи страниц и секций.
- `createPage()` вставляет строку `tbl_page`; `updatePage()` одной транзакцией меняет поля
  страницы и, при смене адреса, переписывает `tbl_page_old_slug`.
- `createSection()`, `updateSection()`, `sectionMove()`, `sectionToggle()`, `sectionDelete()`
  меняют `tbl_page_section`. Ключ секции (`sec_key`) замораживается при создании.
- `deletePage()` удаляет страницу, её секции и историю адресов безвозвратно. Экран конструктора
  с RELEASE 2.1 вызывает `trashPage()`/`trashSection()` из `core/trash.php`: строка уходит
  в `tbl_trash` вместе с полным payload, а живая таблица освобождается.
- `core/duplicate.php` копирует страницу или секцию новыми идентификаторами.
- `core/bulk.php` меняет статус отмеченных страниц прямыми `UPDATE`.

### Новости

- `apps/news/lib/items.php`: `createItem()`, `updateItem()`, `setItemStatus()`,
  `setItemPinned()`.
- `updateItem()` пишет строку и связи тегов одной транзакцией, ведёт историю адресов.
- «Запланировано» у новости не является статусом: это будущий `published_at` при
  `status = PUBLISHED`; публичная лента отбирает материалы по наступившему сроку.

### Товары

- `apps/commerce/lib/catalog.php`: `commerceCreateProduct()`, `commerceUpdateProduct()`,
  `commerceSetProductStatus()`. Правка товара и его рубрик идёт одной транзакцией; атрибуты
  сохраняются отдельным вызовом `commerceSaveProductAttributes()`.

### Заявки, меню, настройки

- Заявки, пункты меню и тексты шапки/подвала пишутся своими сервисами и в контент страниц
  не входят. Ревизии Editorial Pro на них не распространяются.

## 2. Структура хранения

| Таблица | Назначение | Ключ |
| --- | --- | --- |
| `tbl_page` | адресная страница | `id`, уникальный `slug` |
| `tbl_page_section` | секция конструктора | `id`, уникальная пара `(page_id, sec_key)` |
| `tbl_page_old_slug` | прежние адреса | `slug` |
| `tbl_news_item` | новость | `id`, уникальный `slug` |
| `tbl_news_item_tag` | теги новости | `(item_id, tag_id)` |
| `tbl_commerce_product` | товар | `id`, уникальные `slug` и `sku` |
| `tbl_commerce_product_category` | рубрики товара | `(product_id, category_id)` |
| `tbl_audit_log` | журнал действий | автоинкремент |
| `tbl_trash` | корзина | `id`, payload JSON |

Все моменты хранятся в UTC (`DATETIME`), перевод в московское время выполняет только
`core/date.php`. JSON-поля секций (`buttons`, `items`, `settings`) — всегда `'[]'`/`'{}'`,
а не `NULL`.

Главная страница `/` не имеет строки `tbl_page`: её секции живут с `page_id = ''`.
Для ревизий такая страница получает стабильный ключ `home`.

## 3. Идентификация секций

- У секции уже есть стабильный `id` (26 символов, `core/id.php`) и `sec_key` — человекочитаемый
  ключ внутри страницы.
- `sort` задаёт порядок; `visible` — видимость; `kind` и `layout` — вёрстку.
- Перестановка меняет только `sort`, идентификаторы не меняются. Это позволяет сравнивать
  секции по `id`, а не по позиции: перемещение не будет выглядеть как удаление и создание.
- Копирование и вставка создают новые `id` и новые `sec_key`; история копии начинается заново.
- Восстановление ревизии должно возвращать прежние `id`/`sec_key` секций, чтобы ссылки,
  комментарии к секциям и будущие связи оставались осмысленными.

## 4. Что необходимо версионировать

### Страница

- `title`, `slug`, `description`, `status`, `noindex`, `created_at`, `updated_at`;
- полный упорядоченный список секций: `id`, `sec_key`, `kind`, `layout`, `anchor`, `badge`,
  `title`, `lead_text`, `note`, `image`, `image_alt`, `buttons`, `items`, `settings`, `sort`,
  `visible`, `updated_at`;
- SEO-представление: заголовок, описание, canonical (в текущей схеме отсутствует — хранится
  пустым), robots, Open Graph, Schema.org (в текущей схеме не выделены — хранятся пустыми),
  URL и изображения;
- для главной — тот же снимок секций с ключом `home`.

### Новость

- все поля `tbl_news_item`, включая автора, категорию, обложку, дату публикации, статус,
  SEO-поля, `noindex`, закрепление;
- абзацы `body`, теги;
- прежние адреса в снимок не входят: это навигационная история, а не состояние материала.

### Товар

- все поля `tbl_commerce_product`, рубрики и атрибуты.

Система ревизий должна быть расширяемой: тип объекта — строка, снимок собирается
функцией-поставщиком, а неизвестные типы могут добавить приложения через хук.

## 5. Операции, которые могут конфликтовать

1. Два редактора правят поля одной страницы.
2. Один меняет секцию, другой меняет порядок секций.
3. Один удаляет секцию, другой её редактирует.
4. Двое одновременно меняют SEO-поля или статус публикации.
5. Автосохранение приходит после ручного сохранения с устаревшей версией.
6. Повторная отправка запроса после сетевого сбоя создаёт дубль ревизии.
7. Планировщик публикует материал, пока редактор сохраняет черновик.
8. Восстановление старой версии поверх свежих изменений другого сотрудника.

## 6. Как предотвратить потерю изменений

- Каждый материал получает голову версии (`content_heads`) и цепочку ревизий.
- Новый интерфейс передаёт `expected_version`; сервер сравнивает его с головой внутри
  транзакции и при расхождении возвращает конфликт, не записывая данные.
- Старые вызовы без `expected_version` продолжают работать: они получают блокировку головы
  и создают ревизию, но не ломают прежние формы.
- Автосохранение передаёт `idempotency_key`; повтор с тем же ключом возвращает прежний
  результат и не создаёт вторую ревизию.
- Ревизия и изменение материала фиксируются в одной транзакции: либо есть и новое состояние,
  и его снимок, либо нет ни того, ни другого.
- Перед удалением старых ревизий проверяются последняя ревизия, опубликованные версии,
  последняя опубликованная версия и активное согласование.
- Восстановление всегда создаёт новую ревизию с содержимым выбранной; промежуточные
  ревизии не удаляются.

## 7. Совместимость со старыми материалами

- Схема существующих таблиц не меняется. Новые сущности — только новые таблицы.
- Идентификаторы страниц, секций, новостей и товаров не перегенерируются.
- Формат JSON-полей секций не меняется.
- Для старого материала базовая ревизия создаётся из текущего состояния с операцией
  `initial` и источником `import`; это не искусственная история, а честная точка отсчёта.
- Импорт выполняется лениво при первом открытии истории/первом сохранении и пакетно
  командой `bin/cron.php --baseline`; повторный импорт ничего не дублирует.
- Публичные выборки, корзина, предпросмотр, магазин, объявления и курсы не меняют своих
  запросов и продолжают работать без новых таблиц, даже если миграция ещё не применена.

## 8. Переиспользуемые компоненты

- `core/auth.php` — текущий пользователь, роли, проверка «кто правит контентом».
- `core/audit.php` — журнал действий: редакционные операции пишутся в него.
- `core/trash.php` — удаление секций через корзину.
- `core/duplicate.php` — копия материала при конфликте.
- `core/preview.php` — предпросмотр, на него ссылается панель редактора.
- `core/date.php` — единственное место разбора и печати дат.
- `core/request.php`, `core/csrf.php`, `core/response.php` — формы, токен, JSON-ответы.
- `core/options.php` — настройки хранения ревизий; отдельная таблица не нужна.

## 9. Точки интеграции

| Компонент | Точка |
| --- | --- |
| страницы | `updatePage()`, `createPage()`, `section*()` |
| корзина | `trashPage()`, `trashSection()`, восстановление из корзины |
| копирование | `duplicatePage()`, `duplicateSection()` |
| массовые операции | `pagesBulkStatus()` |
| новости | `createItem()`, `updateItem()`, `setItemStatus()`, `setItemPinned()` |
| товары | `commerceCreateProduct()`, `commerceUpdateProduct()`, `commerceSetProductStatus()` |
| маршруты | `core/routes.php`, один экран `/admin/editorial`, API через `POST` с `op` |
| админка | `admin/layout.php`, `pages-edit.php`, `pages-sections.php`, новый `admin-editorial.js` |
| планировщик | `bin/cron.php`, без публичного HTTP-маршрута |

## 10. Решения по реализации

1. Новые таблицы: `content_revisions`, `content_heads`, `editor_locks`, `editor_presence`,
   `editorial_states`, `editorial_comments`, `editorial_tasks`, `editorial_notifications`,
   `scheduled_publications`, `editorial_rates`.
2. Тип и идентификатор контента — строки; снимок — канонический JSON, контрольная сумма
   SHA-256.
3. Оптимистическая блокировка — номер головы; блокировка редактирования — отдельная
   временная запись с heartbeat, она не заменяет проверку версии.
4. Первый релиз использует блокировку на уровне материала, но ревизии и комментарии уже
   привязаны к секциям, поэтому независимое редактирование секций можно включить позже.
5. Планировщик — CLI-скрипт, потому что публикация по обычному просмотру страницы запрещена
   спецификацией. HTTP-маршрута у него нет.
6. Настройки хранения — опции ядра (`getOption()`/`setOption()`), без новой таблицы.
7. Старый формат данных и старые вызовы сохраняются; новые проверки включаются передачей
   `expected_version`/`idempotency_key` из нового интерфейса и API.

## 11. Ограничения первого этапа

- `home` версионируется как страница с ключом `home`.
- Canonical, Schema.org и Open Graph у страниц в текущей схеме отсутствуют; в снимке они
  присутствуют пустыми полями и готовы к появлению реальных значений без миграции формата.
- Курсы и уроки не имеют отдельного административного сохранения в текущем ядре; для них
  доступен общий API ревизий, а базовые ревизии создаются при появлении такого сохранения.
- Рассылка email-уведомлений не включается: уведомления хранятся в центре редакции, точка
  подключения почты оставлена в сервисе.
