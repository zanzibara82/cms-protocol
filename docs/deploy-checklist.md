# Выкладка пилота на виртуальный хостинг

Порядок шагов — спецификация §11. Строки приёмки — §12, двадцать пунктов; напротив каждой
указано, чем она проверяется, потому что «проверено глазами» и «есть тест» — это разные
обещания.

Ни один пароль не попадает в файл, в отчёт и в память: значения читаются из переменных сессии,
боевой `config.php` создаётся на сервере и в git не лежит.

## Переменные своей сессии

```bash
export CMS_DEPLOY_USER='логин SSH'
export CMS_DEPLOY_HOST='адрес сервера'
export CMS_DEPLOY_PATH='/home/логин/cms'          # абсолютный путь проекта
export CMS_DEPLOY_MODE='public'                    # или root, если корень не переносится
```

Здесь четыре переменные — их хватает на все прогоны `scripts/deploy.sh` кроме последнего. Пятая,
`CMS_DEPLOY_URL='https://домен-школы.рф'` (адрес сайта для проверки раскладки), ставится только шагом 5
и специально не стоит в этом блоке: до установщика главная отвечает отказом, поэтому переменная,
экспортированная заранее, делает шаг 3 красным — и это не поломка выкладки, а ровно правильное
состояние ещё не установленного сайта.

`bash scripts/deploy.sh --dry-run` — пробег без записей; первый настоящий запуск делают только
после него.

## Шаг 1. Зонд хостинга (§11.1)

```bash
KEY="$(head -c 18 /dev/urandom | od -An -tx1 | tr -d ' \n')"
BUILD="$(mktemp -d)"
sed "s/^\\\$probeKey = '';/\$probeKey = '${KEY}';/" scripts/hosting-probe.php > "$BUILD/probe.php"
grep -q "probeKey = '${KEY}'" "$BUILD/probe.php" || { echo 'ключ не подставился — на разборе формата sed'; exit 1; }
scp "$BUILD/probe.php" "$CMS_DEPLOY_USER@$CMS_DEPLOY_HOST:$CMS_DEPLOY_PATH/public/probe.php"
curl -sS "https://домен-школы.рф/probe.php?k=${KEY}&smtp=smtp.хостинга&port=587"
rm -rf "$BUILD"
```

Зонд отвечает один раз и удаляет себя. Последняя строка ответа — удалился ли; если `нет`, файл
снимают руками (`ssh … rm public/probe.php`) и не оставляют: он отвечает на запросы о сервере.

У ключа два источника, и это надо знать до пробега: вписанное в копию файла значение перекрывается
переменной окружения хостинга `CMS_PROBE_KEY`, если она задана и не пуста. Переменная нужна там,
где панель не даёт подставить значение в файл перед загрузкой. Если же она задана случайно или
осталась от прошлой проверки, `curl` получит 403 при формально верном ключе — выглядит как поломка
зонда, а на деле ключ просто другой. Поэтому перед пробегом проверяют, что в окружении сайта такой
переменной нет, либо берут ключ из неё и не правят файл.

Что должно быть в ответе: `[+]` напротив PHP ≥ 8.1, шести расширений, `stream_socket_client` и
`session.save_path`; `[!]` напротив document-корня — ожидаемо, если корень ещё не переносили, и
тогда режим `root` с корневым `.htaccess`. `[-]` напротив argon2id — не стопор: bcrypt уже
настроен в `core/auth.php`.

## Шаг 2. Перенос документ-корня

В панели хостинга: корень домена → `<CMS_DEPLOY_PATH>/public`. Если переноса нет —
`CMS_DEPLOY_MODE=root`, и тогда проверка раскладки обязательна (шаг 5): закрытые `core/`, `apps/`,
`sql/`, `config.php`.

## Шаг 3. Файлы

```bash
bash scripts/gate.sh
bash scripts/css
bash scripts/deploy.sh
```

Ворота перед выкладкой — не формальность: `git status` обязан быть пустым, иначе на сервер уйдёт
то, чего нет в репозитории.

Проверка раскладки на этом шаге пропускается, и это правильно. Без `CMS_DEPLOY_URL` скрипт печатает
дословно «CMS_DEPLOY_URL не задан — проверку раскладки пропускаем; шаги 2 и 5 чек-листа делают её
руками.» и завершается нулевым кодом. До установщика главная обязана отвечать отказом, поэтому
красный текст «Отказ: / отвечает …» на шаге 3 означал бы обратное: переменная адреса уже экспортирована,
хотя её черёд только шагом 5, после шага 4.

`scripts/deploy.sh` исключает `/public/uploads/`: картинки, залитые на сервере, в репозитории нет,
и обратная пересылка стёрла бы их. Плата — каталог растёт: при замене обложки прежний файл
остаётся на диске, потому что удалить его безопасно можно только убедившись, что на путь не
ссылается другой материал. Раз в приёмку смотреть содержимое `public/uploads/images/` и
`public/uploads/files/` и лишнее убирать вручную.

## Шаг 4. Настройки и установщик (§11.3, §11.4)

`config.php` на сервере создаёт установщик, а не руки: образец `config.sample.php` остаётся в дереве
источником значений по умолчанию, копировать его и вписывать ключи вручную больше не нужно. Каталог
проекта обязан быть доступен на запись пользователю, под которым работает PHP, — туда шаг 1 пишет
файл. В браузере:

1. `https://домен/setup.php` — шаг 1: хост и порт базы, полное имя базы (с префиксом логина),
   пользователь и пароль базы, префикс таблиц `tbl_`, адрес сайта **без слэша в конце** и его
   название. Успех шага — записанный `config.php` и переход на шаг 2; любой отказ печатается на
   экран и не пишет ни файл, ни отметку сессии.
2. `https://домен/setup.php?step=admin` — шаг 2: название сайта, почта и имя администратора, пароль
   дважды (не короче 10 символов). Открывается только после успешного шага 1: без отметки сессии
   адрес возвращает на шаг 1 с объяснением. Шаг применяет схему ядра из
   `sql/0001_core_baseline.sql`, создаёт первого администратора, ставит замок и ведёт на `/login`;
3. `https://домен/admin/apps` → «Новости» → «Установить»;
4. повторный заход на `setup.php` обязан ответить 404 (замок).

Форма шага 1 собирает восемь ключей: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASS`,
`TABLE_PREFIX`, `SITE_URL`, `SITE_NAME`. Остальные ключи она не спрашивает — их значения берутся из
образца и правятся вручную в уже записанном `config.php`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASS`, `MAIL_FROM` (в пилоте письма не ходят, пустые значения законны), `TIMEZONE` и служебные
`EXTRA_APPS_DIR`, `EXTRA_THEME_DIR` (их читают только тесты, на сервере они остаются пустыми).
`TIMEZONE` входит в список обязательных ключей загрузчика, поэтому стирать его значение нельзя: без
него сайт откажется запускаться.

**Режим СУБД.** Перед установкой в панели хостинга (phpMyAdmin) выполняют `SELECT @@sql_mode` и
проверяют, что в списке нет `NO_BACKSLASH_ESCAPES`. Поиск раздела «Новости» снимает спецсимволы
`%` и `_` обратным слэшем и объявляет знак снятия явно (`LIKE ? ESCAPE ?`), поэтому работает в любом
режиме; но сам обратный слэш в роли снимающего живёт только пока `NO_BACKSLASH_ESCAPES` отсутствует,
и включённый на уровне сервера режим меняет поведение прочих запросов. В конфигурации стенда режим
нигде не закреплён: `grep -rn "sql_mode"` по `docker-compose.dev.yml`, `docker/`, `sql/` и `scripts/`
даёт пустой вывод, а единственным упоминанием в репозитории остаётся тест набора `tests/db`, который
включает режим на время проверки и снимает его. Поэтому проверять режим придётся руками на боевом
хостинге — локальный стенд с MySQL в контейнере этого не подтверждает. Зонд хостинга
`scripts/hosting-probe.php` режим не печатает: по документированному проекту он не читает базу и
`config.php`, а `sql_mode` без подключения к базе не узнать.

Права `600` на `config.php` — пункт приёмки, а не следствие копирования: их выставляет сам шаг 1
(`umask(0o077)` на время записи плюс `chmod()` временного файла до переименования). Проверка на
сервере — `ls -l config.php` показывает `-rw-------`. Если файловая система хостинга права не
удержала, шаг 2 встречает человека плашкой предупреждения, и тогда права выставляют руками (панель
или `chmod 600 config.php`).

**Защищённый канал.** Признак `Secure` у куки сессии берётся из `isHttps()` (`core/request.php`), а
та смотрит только на `$_SERVER['HTTPS']` и порт `443`; заголовок `X-Forwarded-Proto` ядро не читает
намеренно — его подделывает любой клиент. Значит защищённый канал обязан терминироваться на самом
веб-сервере хостинга, а не на промежуточном прокси, который передаёт запрос дальше по http.
Проверка: адрес сайта начинается с `https://`, канал держит веб-сервер, а кука сессии приходит с
`Secure`. Редирект http→https в `public/.htaccess` построен на том же условии `%{HTTPS} !=on`, поэтому
при терминале на прокси не работает и он. Нового ключа в настройках не появляется.

## Шаг 5. Проверка на месте (§11.5)

Здесь появляется пятая переменная — только сейчас сайт установлен и главная обязана отвечать. Перед
прогоном проверяют, что она не пуста: `CMS_DEPLOY_URL=''` скрипт читает так же, как незаданную, —
печатает строку пропуска и завершается нулевым кодом. Пропуск на этом шаге означает не зелёную
выкладку, а непройденную приёмку.

```bash
export CMS_DEPLOY_URL='https://домен-школы.рф'
test -n "$CMS_DEPLOY_URL" || { echo 'CMS_DEPLOY_URL пуст — проверка раскладки не сделана'; exit 1; }
bash scripts/deploy.sh
curl -sS https://домен/robots.txt
curl -sS https://домен/sitemap.xml | head -20
```

Ожидаемый признак успеха — последняя строка «Раскладка закрыта как надо. Дальше — шаги 3..6
docs/deploy-checklist.md.», ноль строк «Отказ:» и нулевой код возврата. Скрипт не печатает коды
ответа при удаче: обход `/` и `/assets/app.css` (`scripts/deploy.sh:96-104`) пишет «Отказ:» только на
отличии от 200, поэтому признак — именно отсутствие «Отказ:» плюс нулевой код, а не наличие двух
строк с `200`. Замерять этот признак надо на живом хостинге: локальный стенд на `php -S` не отдаёт
боевой адрес, и здесь прочитан только код скрипта.

В базе (`tbl_app_migration` — ровно две строки установки, `tbl_app_installation` — `version`
`1.0.0`), в браузере — `/news`, `/news/admin` анонимом (403 или редирект на `/login`), три
стартовые рубрики, HTTPS и `secure`-куки.

## Шаг 6. Приёмка §12 на хостинге

Повторить пункты 1–18 тем же способом, что и на локальном стенде: тесты не переносим (на сервере
`tests/` нет), проверяем экранами. Пункты 19–20 — это ворота и SMTP-заглушка, они на хостинге не
воспроизводятся по определению: почтовый клиент проверен на mailpit в Docker (задача 10), а на
боевом сервере в пилоте письма не отправляются (§3).

Две строки таблицы ниже помечены «не проверено локально, требует стенда хостинга» — 17 и 20. Локально
за них отвечает обход `tests/http`, который ходит без браузера и без настоящего почтового сервера,
поэтому закрытыми эти пункты считаются только после прогона на хостинге.

## Откат

Боевая база не пересоздаётся никогда: миграции раздела дополняющие (Global Constraints), а
`scripts/db-reset` трогает только `cms_test`. Откат выкладки файлов — повторный `rsync` из коммита
прошлой версии (`git worktree add ../old <commit>` и `CMS_DEPLOY_PATH=… bash ../old/scripts/deploy.sh`).
