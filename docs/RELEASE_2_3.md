# RELEASE 2.3 «Конструктор контента»: свои типы записей, поля, связи и глобальные блоки

## 1. Что входит в релиз

- Пользовательские типы записей: редакция заводит раздел («Статьи», «Сотрудники», «Проекты»)
  и получает список, публичные адреса и SEO-поля без правки кода.
- Конструктор полей типа: строка, многострочный текст, текст с абзацами, число, флажок, выбор
  из списка, картинка, ссылка, дата и связь с записями.
- Связи между записями: поле вида `relation` хранит упорядоченный список записей выбранных типов;
  связь сохраняется в той же транзакции, что и значения полей.
- Глобальные блоки: переиспользуемые фрагменты (заголовок, подзаголовок, текст, картинка, ссылка,
  вёрстка), которые конструктор страниц вставляет видом `global_block`.
- Мягкий архив вместо удаления: тип, поле и глобальный блок снимаются с показа, но их данные,
  история адресов и ревизии остаются в базе.
- История RELEASE 2.2 распространена на новые сущности: `entry` и `block` — такие же типы
  ревизий, как `page`, `news` и `product`, со сравнением, восстановлением, оптимистической
  блокировкой и идемпотентностью.
- Планировщик RELEASE 2.2 умеет публиковать записи по расписанию: запись получает статус
  `scheduled`, задача ложится в `tbl_scheduled_publications`, публикует её `bin/cron.php`.

Релиз дополняет RELEASE 2.2 и не меняет таблицы страниц, секций, новостей, товаров, объявлений,
уроков и заявок. Идентификаторы и форматы хранения прошлых релизов остаются прежними.

## 2. Новые сущности

| Сущность | Таблица | Назначение |
|---|---|---|
| Тип записи | `tbl_content_type` | Раздел пользовательского контента: адрес, название, описание. |
| Поле типа | `tbl_content_field` | Описание поля: неизменяемый ключ, вид, подпись, обязательность, варианты. |
| Запись | `tbl_content_entry` | Материал типа: адрес внутри типа, заголовок, статус, JSON значений, SEO. |
| Связь | `tbl_content_entry_relation` | Упорядоченная связь записи с записью по ключу поля. |
| Старый адрес типа | `tbl_content_type_old_slug` | 301 с прежнего адреса раздела на живой. |
| Старый адрес записи | `tbl_content_entry_old_slug` | 301 с прежнего адреса материала на живой. |
| Глобальный блок | `tbl_global_block` | Переиспользуемый фрагмент для конструктора страниц. |

### 2.1. Идентификаторы и адреса

- `id` всех новых строк — ULID из `newId()`, как у остальных сущностей ядра.
- Адрес типа — `/{type-slug}`, адрес записи — `/{type-slug}/{entry-slug}`.
- Слаг типа не может совпадать с зарезервированными первыми сегментами ядра и приложений
  (`admin`, `login`, `news`, `shop`, `seo`, `sitemap`, `preview` и т. д.), с адресом страницы и с
  адресом другого типа. Слаг записи уникален внутри типа.
- Смена слага типа или записи пишет прежний адрес в таблицу старых слагов. Прежний адрес
  отвечает 301, пока владелец опубликован; черновик и архив отвечают 404 и не выдают себя.
- Ключ поля (`field_key`) после создания не меняется: по нему лежат значения в JSON. Поле можно
  убрать и вернуть тем же ключом — значения останутся. Переименование подписи и смена вида
  допустимы, данные при этом не удаляются.

### 2.2. Статусы

- Запись: `draft`, `published`, `scheduled`, `archived`.
- Публичный сайт показывает только `published`; сотрудник с правом `manage` видит черновик по
  прямому адресу как предпросмотр (страница отдаётся с `noindex`).
- `scheduled` ставит планировщик RELEASE 2.2: запись не видна до срока, после срока её публикует
  `bin/cron.php`, а не обычный просмотр страницы.
- Глобальный блок: `active = 1/0`. Неактивный блок не печатается на странице и не предлагается
  в конструкторе.

## 3. Схема базы

Файл `sql/0005_release23.sql` создаёт семь таблиц и ничего не меняет в существующих. Второй файл,
`sql/0006_release23_layouts.sql`, добавляет страницам и секциям поля раскладки. Все имена —
префикс настроек (`tbl_` по умолчанию). Повторно файлы не применяются: установщик и обновление
ядра ведут журнал `tbl_app_migration`, а `0005` вдобавок защищён `IF NOT EXISTS`.

Ключевые ограничения:

- `tbl_content_entry` — `UNIQUE (type_id, slug)`, индексы по статусу и дате правки;
- `tbl_content_field` — `UNIQUE (type_id, field_key)`;
- `tbl_content_entry_relation` — `UNIQUE (from_entry_id, field_key, to_entry_id)`;
- `tbl_content_type` и `tbl_global_block` — уникальный `slug`;
- старые слаги не уникальны: это история переездов, свежая строка важнее старой.

Проверки перечней (статус, вид поля, вёрстка блока) живут в PHP: `CHECK` в MySQL 5.7 молча
игнорируется, поэтому полагаться на него нельзя.

## 4. Права

| Действие | Кто |
|---|---|
| Создание, правка, архив и восстановление типа | Администратор |
| Конструктор полей типа | Администратор |
| Создание и правка записи | Редактор и администратор (`editorialCan('edit')`) |
| Публикация, снятие с публикации, архив записи | Администратор (`editorialCan('publish')`) |
| Планирование публикации записи | Администратор (`editorialCan('schedule')`) |
| Глобальные блоки | Администратор |
| Просмотр списка записей | Редактор и администратор |

Права проверяются на сервере дважды: воротами маршрута и внутри доменной операции. Скрытая
кнопка не считается защитой — POST без права получает отказ и не меняет базу.

## 5. История и целостность

- Сохранение записи идёт одной транзакцией: проверка версии (`contentRevisionGuard`), строка
  записи, значения полей, связи, старый адрес и ревизия (`contentRevisionCommit`). Ошибка любой
  части откатывает всё.
- `expected_version` сохраняет поведение RELEASE 2.2: при гонке возвращается конфликт с актуальной
  версией и её ревизией, чужая правка не затирается.
- `idempotency_key` повторного запроса возвращает прежнюю ревизию, а не создаёт вторую; повтор
  создания с тем же ключом возвращает уже созданную запись или блок.
- Вызовы без `expected_version` и `idempotency_key` работают как раньше — совместимость с API и
  старыми формами сохраняется.
- Восстановление ревизии записи возвращает заголовок, адрес, статус, SEO, значения полей и связи.
  Возврат опубликованной или архивной версии требует права публикации; версия со статусом
  «запланировано» не восстанавливается — расписание создаётся заново.
- Ревизии глобальных блоков открывает и восстанавливает только администратор: история блока не
  подменяет гейт управления блоками.
- Удаления строк нет: архив типа, поля, записи и блока обратим.

## 6. Публичные страницы и конструктор

- `/{type-slug}` — список опубликованных записей типа, сначала новые по `published_at`.
- `/{type-slug}/{entry-slug}` — запись: заголовок, SEO, поля в порядке конструктора, связи.
- `/{type-slug}` и `/{type-slug}/{entry-slug}` не перекрывают страницы и приложения: точные
  маршруты разделов выигрывают у параметрических, а страница не может занять слаг типа.
- Прежние адреса страницы, типа и записи держат 301: новый материал или раздел не может занять
  чужой старый адрес.
- Вид конструктора `global_block` получает в настройках слаг блока и печатает его текущее
  содержимое. Пустой, архивный или неизвестный слаг не печатает ничего.
- Карта сайта (`sitemap_urls`) получает адреса типов и опубликованных записей; сквозной поиск
  редакции — группу «Записи» и «Глобальные блоки».

## 7. Миграция

1. Сделайте резервную копию базы и файлов.
2. Обновите файлы сборки до RELEASE 2.3 (`CORE_VERSION = 1.5.0`).
3. Откройте `/admin/apps` и примените обновление ядра: `sql/0005_release23.sql` создаст новые
   таблицы, `sql/0006_release23_layouts.sql` добавит поля раскладки. Существующие таблицы не
   пересоздаются.
4. Проверьте `/admin/content`: раздел должен открыться, список типов может быть пустым.
5. Заведите первый тип, добавьте поля и запись, опубликуйте её и откройте публичный адрес.

Откат: остановите публикацию новых записей, верните файлы предыдущей сборки. Новые таблицы можно
оставить — ядро 1.4.0 их не читает. Удалять таблицы нужно только после выгрузки данных, если они
больше не нужны: удаление необратимо.

## 8. Проверка после установки

- `/admin/content` открывается администратору; редактор видит типы и записи, но не формы
  управления типами и блоками и не историю блоков.
- Создание типа с занятым или служебным адресом отклоняется с понятной причиной.
- Поле с обязательным флажком не даёт сохранить пустое значение.
- Архивное поле не теряет значение при правке записи: возвращённое тем же ключом поле показывает
  прежние данные, а архивная связь не исчезает.
- Смена адреса записи сохраняет прежний адрес: он отвечает 301 на новый.
- Сохранение с устаревшей версией показывает конфликт, а не затирает чужую правку.
- Повтор POST с тем же `idempotency_key` не создаёт вторую ревизию, запись или блок.
- Черновик записи не открывается гостю (404) и виден сотруднику с `noindex`.
- Архив типа убирает его с сайта, но запись и ревизии остаются в базе.
- Глобальный блок вставляется в страницу конструктором и печатает те же поля, что в своём
  редакторе; архивный блок не печатается.

## 9. Тесты

- `tests/unit/Release23ContentRulesTest.php` — адреса, ключи полей, проверка значений, ссылки,
  перечни статусов и видов.
- `tests/db/Release23ContentTest.php` — таблицы, тип, поля, запись, связи, конфликты версий,
  идемпотентность, восстановление ревизии, старые адреса, глобальные блоки.
- `tests/http/Release23HttpTest.php` — вход и права ролей, CSRF, создание типа, запись, публикация,

## 10. Безопасность и адаптивность: стражи, добавленные после приёмки

Четыре проверки закрывают места, где правило существовало в коде, но ничем не удерживалось:
поломка проходила весь набор зелёной.

- `tests/unit/CommerceWebhookUrlTest.php` — адрес вебхука не указывает на внутреннюю сеть.
  Запрос шлёт сам сервер, а адрес задаёт администратор магазина: без запрета приёмником
  становится панель хостинга на `127.0.0.1`, база на `localhost:3306` или служба метаданных
  облака на `169.254.169.254` (SSRF). Проверка идёт по разобранному адресу, по литералам и по
  разрешённым именам; запрет шире «приватных диапазонов» PHP — `100.64.0.0/10` и диапазоны
  документации тоже закрыты. Повторная проверка стоит в транспорте перед самым `curl`: имя
  может разрешиться внутрь уже после сохранения (DNS rebinding).
- `tests/http/SecurityHeadersTest.php` — каждый ответ (200, 403, 404, лента, карта сайта) несёт
  `nosniff`, `X-Frame-Options`, `Referrer-Policy` и CSP с `script-src 'self'` и
  `frame-ancestors 'self'`. HSTS отдаётся только по HTTPS: по обычному HTTP браузер запомнил
  бы его для домена на год и сломал локальную приёмку.
- `tests/guard/SessionFlagsTest.php` — флаги сессионной куки читаются по исходнику
  `core/session.php`: `HttpOnly`, `SameSite=Lax`, `secure` при HTTPS, `use_strict_mode`,
  перевыпуск идентификатора при входе до записи `user_id`. Стенд поднимается по HTTP, браузера
  в контейнере нет, поэтому иначе эти условия не проверялись вовсе.
- `tests/guard/ResponsiveCoverageTest.php` — список экранов в `scripts/responsive-check.mjs`
  обязан покрывать все статические маршруты `/admin*` из роутеров и не содержать мёртвых
  адресов. До правки в списке были только экраны новостей, а конструктор страниц, медиатека,
  редакция, настройки, заявки и журнал — ровно те экраны, где обрезку и разъезжающиеся поля
  ловили дважды, — проверялись только руками.
