# RELEASE 2.3 — макеты страниц и ширина секций (часть B)

Часть A дала реестр тем и экран «Дизайн → Темы»: тему можно установить, переключить и
вернуть к встроенной. Каркас при этом оставался один на весь сайт — шапка, подвал и
контейнер `max-w-5xl` были у каждой страницы.

Часть B делает каркас настраиваемым: макет страницы и ширина блока.

## Что появилось

### Макет страницы (`tbl_page.layout`)

Девять макетов, каждый — набор флагов, а не отдельный шаблон:

| Ключ | Подпись | Шапка | Подвал | Каркас |
|---|---|---|---|---|
| `default` | Стандартная страница | да | да | `max-w-5xl` |
| `wide` | Широкая страница | да | да | `max-w-6xl` |
| `landing` | Лендинг без шапки и подвала | нет | нет | без отступов |
| `blank` | Пустой макет (Blank Canvas) | нет | нет | без отступов |
| `no-header` | Без шапки | нет | да | `max-w-5xl` |
| `no-footer` | Без подвала | да | нет | `max-w-5xl` |
| `sidebar-left` | Сайдбар слева | да | да | сетка с колонкой |
| `sidebar-right` | Сайдбар справа | да | да | сетка с колонкой |
| `two-sidebars` | Две боковые панели | да | да | сетка с двумя колонками |

**Неизвестное значение откатывается к `default`.** Макет приходит из базы и из формы; чужая
строка не должна оставлять страницу без шапки или давать белый экран. Проверяется это
правилом `pageLayoutPlan()`, а не доверием к значению.

**Смена макета не трогает данные.** Блоки, адрес, SEO, статус публикации и медиа остаются
прежними — меняется только обвязка вокруг содержимого. Это записано в подсказке поля формы.

### Ширина блока (`tbl_page_section.width`, `tbl_page_section.width_custom`)

| Ключ | Что делает |
|---|---|
| `standard` | Контейнер `max-w-5xl` — прежний вид всех блоков |
| `wide` | Контейнер `max-w-6xl` |
| `full` | Блок на всю ширину экрана, вложенного ограничителя нет |
| `custom` | Ширина человека, 320–2400 px, подрезается пределами |

Ширина есть **у всех** видов блоков, а не у отдельных: это свойство секции, а не вида.
Пределы `320…2400` держатся правилом: значение вне границ подрезается, а не отклоняется —
страницу уже открыли, и потерять её из-за одного числа хуже, чем подрезать.

**Full Width Section + Inner Content Container.** «Полная ширина» не печатает вложенный
контейнер вовсе: человек сам решает, ограничивать ли содержимое. Остальные ширины печатают
контейнер, и блок центрируется сам.

## Как устроено

Правила живут в `core/page-layout.php`: перечни, подписи, пределы и разбор в флаги.
Классы разметки — в теме: `theme/layout.php` (каркас), `theme/partials/section-open.php`
(контейнер блока), `theme/partials/sidebar.php` (боковая панель).

Такое разделение не косметика. Сборка стилей читает только объявленные каталоги разметки,
и класс, написанный в ядре, не попал бы в артефакт: страница потеряла бы оформление, а
страж `StyleSourceTest` покраснел бы на просвете. Первая версия части B держала классы в
ядре — страж поймал это сразу.

Новый макет добавляется строкой в `PAGE_LAYOUTS` и `PAGE_LAYOUT_NAMES`: каркас ветвится на
флагах, а не на именах макетов, поэтому шаблон править не нужно.

## Миграция

`sql/0006_release23_layouts.sql`:

```sql
ALTER TABLE tbl_page ADD COLUMN layout VARCHAR(32) NOT NULL DEFAULT 'default' AFTER noindex;
ALTER TABLE tbl_page_section
  ADD COLUMN width VARCHAR(16) NOT NULL DEFAULT 'standard' AFTER layout,
  ADD COLUMN width_custom INT NOT NULL DEFAULT 1200 AFTER width;
```

**Существующие страницы выглядят как раньше.** `default` и `standard` воспроизводят
прежний каркас и прежний контейнер `max-w-5xl`, поэтому миграция ничего не переставляет:
ни адресов, ни содержимого, ни SEO.

Файл только дополняет схему и не трогает значения других колонок.

## Совместимость с темами

Флаги макета доезжают до каркаса переменной `$layout` — тему это не ломает: старая тема,
которая не читает `$layout`, печатает свою обвязку, как раньше. Тема, которая хочет
поддержать макеты, читает `pageLayoutPlan($layout)` и сама решает, что печатать.

## Назначение макета (часть C)

Макет был только у страницы. Тип контента и его записи получали стандартную обвязку всегда:
лендинг из архива каталога был невозможен, хотя сами макеты существовали.

Приоритет из спецификации §14 — объект → тип → умолчание:

| Ступень | Где хранится | Кто перебивает |
|---|---|---|
| Объект (страница) | `tbl_page.layout` | всё ниже |
| Тип контента | `settings.layout` в `tbl_content_type` | умолчание |
| Умолчание сайта | — | — |

**Пустое и неизвестное значение — это «не назначено», а не «показать пусто».** Разница
существенная: назначение приходит из базы и из формы, и если читать пустое как решение, каждый
новый тип ломал бы обвязку сайта. Правило `pageLayoutAssigned()` возвращает либо имя из
перечня, либо пустую строку, и решение принимает следующая ступень.

Настройки типа — JSON-колонка `settings`, а не отдельное поле: настроек со временем станет
больше (шаблон карточки, колонки списка, правила SEO), и каждая новая требовала бы `ALTER`.
Пустой макет **убирает ключ** из настроек, а не пишет пустую строку: иначе тип перебивал бы
умолчание сайта пустым значением, и лендинг на всём сайте стал бы невозможен.

## Библиотека готовых шаблонов (часть K)

Готовые наборы блоков живут в `core/template-library.php`: 17 шаблонов в 16 категориях —
главная школы, страница курса, лендинг продажи курса, страница преподавателя, контакты, о
компании, услуги, лендинг продукта, каталог, отзывы, вопросы, тарифы, новости, статья,
благодарность, портфолио, акция.

Шаблон — это список блоков **тех же видов**, что у конструктора. Второго набора разметки нет:
страница, собранная шаблоном, правится в обычном редакторе, и блок выглядит ровно так же, как
поставленный руками.

**Три правила применения:**

1. **Блоки добавляются к существующим.** Шаблон — заготовка, а не замена: собранную страницу
   нельзя терять от одного нажатия. Замена — отдельный флажок.
2. **Замена убирает прежние блоки в корзину**, а не удаляет: оттуда их можно вернуть.
3. **Всё одной транзакцией.** Половина шаблона на странице хуже, чем ничего: предел секций,
   занятый якорь или сбой посреди набора откатывают применение целиком.

Ставит блоки `createSection()` — предел, уникальность якорей и ревизия проверяются теми же
правилами, что и при ручной сборке. Предел считается **до** вставки: иначе применение упёрлось
бы в него посреди шаблона.

Экран — `/admin/templates` (вкладка «Шаблоны»), право конструктора (`login`): шаблон ставит
содержимое, а не меняет оформление всего сайта. Фильтр категории живёт в адресе; неизвестная
категория даёт пустой список, а не весь каталог.

Страж `TemplateLibraryTest` сверяет каталог с ядром: виды блоков из `PAGES_KINDS`, якоря не
повторяются внутри шаблона, набор укладывается в пределы формы, категория и макет объявлены,
ни один блок не пуст. Пустой блок — самая тихая ловушка: сервер отвечает 200, страница
открывается, а на месте блока пустая рамка.

## Варианты шапки и подвала (часть F/G)

Полосы шапки и подвала были единственным видом: знак сайта слева, пункты меню и вход справа.
Поменять раскладку или убрать меню из полосы было нечем, хотя макеты страниц уже работали.

Вариант — **набор флагов**, а не отдельный шаблон, по той же причине, что и макет: полоса одна,
меняется её состав и раскладка. Новый вариант добавляется строкой в `HEADER_VARIANTS`, шаблон
править не нужно.

| Шапка | Флаги | Что видно |
|---|---|---|
| `standard` | меню, вход | знак сайта слева, пункты и вход справа — прежний вид |
| `minimal` | вход | только знак сайта и вход; пункты меню остаются в подвале |
| `centered` | меню, по центру | знак сайта по центру, вход и пункты под ним |
| `topline` | меню, верхняя полоса | строка мелким кеглем над шапкой |

| Подвал | Колонки меню | Что видно |
|---|---|---|
| `standard` | до 4 | прежний вид: все разделы меню |
| `compact` | до 2 | компактная раскладка |
| `plain` | 0 | брендовый ряд и копирайт, без колонок |

**Колонки печатаются только для существующих разделов.** Вариант «без колонок» не рисует
пустую сетку, «компактный» не оставляет дыр: число — предел, а не обязательство.

**Неизвестное значение означает стандартный вид.** Значение приходит из опции, то есть из базы
и формы; подделанный POST не должен оставить сайт без шапки. Проверяет правило `headerPlan()`,
а не доверие к строке.

**Вход печатается при любом варианте.** Без него посетитель не попадёт в админку с телефона, а
режим техобслуживания нечем было бы снять.

Экран — `/admin/settings`, рядом с логотипами и текстами: вариант полосы это тоже настройка
сайта, а не отдельное действие. Сохраняется той же транзакцией, что и остальные поля.

Классы разметки живут в партиалах темы (`header.php`, `header-brand.php`, `header-menu.php`,
`header-account.php`, `footer.php`). Сборка не собирала их из скобок: страж экранирования
разрешает под пометкой `@safe html` только агрегаторы разметки и вызовы `partial()`, а страж
зон нажатия читает классы значения атрибута — за переменной `min-h-[44px]` он его не видит.

## Что осталось от мастер-промпта

Сделано: PHASE A (аудит), PHASE B (менеджер тем), PHASE D (макеты и ширина), PHASE C
(назначение по типам контента), PHASE J (Design System — палитра и типографика), PHASE L
(обмен оформлением через JSON), PHASE K (библиотека готовых шаблонов), PHASE F/G в части
вариантов шапки и подвала.

Не сделано: PHASE E (Template Studio — визуальный конструктор), остаток PHASE F/G
(конструктор полос по элементам: логотип, поиск, корзина, языки), PHASE H (библиотека
паттернов как отдельный каталог вставки), PHASE M (интеграция с приложениями в полном объёме),
PHASE N (тестирование релиза), PHASE O (релиз).

Отдельно не сделано: **установка темы из ZIP**. Она требует своего набора тестов
безопасности — Zip Slip, символические ссылки, права файлов, типы содержимого, — поэтому
каталог `themes/` наполняется файлами на сервере, а экран показывает то, что уже лежит.

Заглушек вместо этих частей нет: экраны, которые ничего не делают, хуже их отсутствия.
